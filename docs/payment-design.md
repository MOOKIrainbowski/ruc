# 현금 충전 자동 지급 — 설계

> 작성 2026-10-01 · **승인 2026-10-02** · 구현 완료 (로컬 E2E 29/29) — 결과는 맨 아래 §9.
>
> 목표: 유저가 **토스 개인 계좌**로 입금하면 입금 내역을 그 유저의 주문과 맞춰 보고,
> 산 상품을 자동으로 지급합니다.
>
> 웹 UI(`/charge`)는 이미 있습니다 (`CHARGE_ENABLED` 로 꺼 둔 상태). 이 문서는
> 그 뒤에서 도는 **입금 감지 → 매칭 → 지급** 을 다룹니다.

---

## 0. 전제와 제약

| 전제 | 결과 |
|---|---|
| 토스 **개인** 계좌에는 공식 입금 웹훅 · 거래내역 API 가 없습니다 | 입금을 "알아내는" 방법부터 골라야 합니다 (§1) |
| 백엔드 서버 · RCON 은 `127.0.0.1` 전용입니다 (`conversation.md` §3) | Vercel 에서는 지급할 수 없습니다. **결제 백엔드는 MOOKI 프로세스 안에** 둡니다 |
| 봇 ↔ 서버 통로는 전부 **RCON 명령 + 한 줄 응답** 규격입니다 (§6.27, `RUC[A-Z]+ <결과>`) | 결제도 같은 규격의 새 명령 `rucpay` 를 씁니다 |
| 4개 서버가 DB 하나를 공유합니다 (H2 → 운영에서 MySQL) | 주문 · 입금 · 지급 기록은 **게임 DB** 에 둡니다. 백업(§6.46) · MySQL 이전에 같이 따라갑니다 |
| 호스팅이 아직 없습니다 (Q1) | 입금 알림을 받는 웹훅은 외부에서 닿아야 합니다 → **호스팅 또는 playit.gg 터널 이후에 운영 가능.** 로컬에서는 모의 입금으로 끝까지 검증합니다 |
| Q5(통신판매업 신고)가 미해결입니다 | 코드는 만들되 **운영 켜기는 Q5 해결 후** (§7) |

## 1. 입금 감지 방식 비교

| 방식 | 동작 | 신뢰성 | 비용 | 난이도 | 약관 · 법 리스크 |
|---|---|---|---|---|---|
| **A. 안드로이드 알림 전달** | 운영자 폰의 토스 앱 입금 푸시를 알림 접근 권한 앱(직접 만든 앱 또는 MacroDroid · Tasker)이 읽어 MOOKI 웹훅으로 POST | 🟡 중. 폰이 꺼지거나 · 배터리 최적화 · 토스 앱 업데이트로 **알림 문구가 바뀌면 조용히 멈춥니다** | 0원 (남는 폰 1대) | 중 | 🟡 자기 기기의 자기 알림을 읽는 것이라 스크래핑은 아닙니다. 다만 **개인 계좌로 반복 영업 수입**을 받는 것 자체가 은행의 "사업 목적 이용" 의심 · 세무 신고 대상이 될 수 있습니다 |
| **B. 오픈뱅킹 / 거래내역 조회 API** (금융결제원, CODEF · 쿠콘 등) | 계좌 거래내역을 주기적으로 조회 | 🟢 높음 | 유료 (건당 · 월정액) | 중 | 🔴 **이용기관이 사업자여야** 합니다. 개인은 가입 불가 → 지금은 선택 불가 |
| **C. PG 가상계좌** (토스페이먼츠 · 포트원) | 주문마다 가상계좌 발급, 입금되면 PG 가 **서명된 웹훅** 전송 | 🟢 가장 높음 (공식) | 건당 약 300원 + 가입비 | 하 (문서화된 API) | 🟢 정석. 단 **사업자등록 + 통신판매업 신고 필수** |
| **D. 관리자 수동 승인** | 운영자가 토스 앱을 보고 디스코드 버튼으로 "입금 확인" | 🟢 높음 (사람이 봄) · 🔴 느림 (운영자 부재 시 수 시간) | 0원 | 하 | 🟢 없음 (단, 개인 계좌 리스크는 A 와 같음) | ✅

### 추천: **D + A 하이브리드로 시작 → 사업자 전환 시 C 로 교체**

1. **기본은 D (수동 승인).** 모든 주문이 디스코드 관리자 채널에 버튼과 함께 올라옵니다. 이것만으로도 시스템이 완결됩니다.
2. **A 는 "자동 승인 도우미"** 로 얹습니다. 알림이 들어와 **코드와 금액이 정확히 맞으면** 사람 대신 승인합니다. 조금이라도 애매하면 D 의 대기열로 넘깁니다. A 가 죽어도 D 로 돌아갈 뿐 **입금이 사라지지 않습니다.**
3. **C 로 바꿀 때는 입금 소스 어댑터 하나만 추가**합니다. 주문 · 매칭 · 지급 · 기록은 그대로입니다 (§4 의 `source` 컬럼).

A 를 단독으로 쓰지 않는 이유: 알림 문구가 바뀌는 순간 **에러 없이** 매칭이 0건이 됩니다. 사람 대기열이 받쳐 줘야 "돈은 받았는데 아무도 모르는" 상태가 생기지 않습니다. 그래서 **"마지막 알림 수신 후 N시간 무소식" 경고**도 넣습니다 (§6).

## 2. 유저 매칭

### 2.1 주문은 디스코드에서 만듭니다

```
/충전 상품:<상품>   → 봇이 DM(+ 임시 응답)으로 주문 코드 · 금액 · 계좌 · 만료 시각 안내
```

- **D10 인증을 마친 디스코드 계정만** 주문할 수 있습니다. 인증이 디스코드 ID ↔ 마크 UUID 를 이미 확실하게 묶어 두었으므로, 주문 시점에 **누구에게 지급할지가 확정**됩니다. 웹에서 닉네임을 입력받는 방식은 오타 · 사칭 문제가 생깁니다.
- 웹(`/charge`)은 상품 안내와 계좌 복사만 합니다 — 웹에는 상태가 없고 Vercel 에서 돌아도 됩니다.

### 2.2 식별 코드

| 항목 | 결정 | 이유 |
|---|---|---|
| 형식 | `R` + 숫자 4자리 (예: `R4821`) | 입금자명 칸이 은행마다 짧습니다(한글 7자 · 영숫자 10자 안팎). 닉네임(최대 16자)은 잘립니다 |
| 입금자명 | **코드만.** 닉네임 · 실명 아님 | 동명이인 · 오타 매칭 문제가 사라지고, 입금자 실명을 수집하지 않아도 됩니다 |
| 금액 끝자리 구분 | **쓰지 않음** | 코드로 충분하고, "5,000원 상품인데 5,017원 보내세요" 는 유저에게 혼란을 줍니다 |
| 발급 | 활성 주문 · **최근 7일** 내 코드와 겹치지 않게 무작위 | 만료 후 늦게 입금된 돈도 어느 주문인지 모호하지 않게 (§2.4) |
| 생성 제한 | 1인당 미결제 주문 **최대 2개** · 생성 쿨타임 1분 | 코드 공간(9,000개) 고갈 · 도배 방지 |

### 2.3 만료

- 주문 후 **60분** (`products.json` 의 `orderTtlMinutes`). 지나면 `EXPIRED`.
- 만료 10분 전 DM 알림은 하지 않습니다 (스팸). 주문 응답에 만료 시각을 명시합니다.

### 2.4 이상 상황 처리

| 상황 | 판정 | 처리 |
|---|---|---|
| 코드 일치 + 금액 일치 + `PENDING` | **자동 매칭** | 지급 |
| 코드 일치 + 금액 일치 + `EXPIRED` (7일 이내) | **자동 매칭 (늦은 입금)** | 지급 + 로그에 `late` 표시. 코드를 7일간 재사용하지 않으므로 모호하지 않습니다 |
| 코드 일치 + **금액 불일치** | `REVIEW` | 관리자 대기열. 버튼: [차액 무시하고 지급] [환불 처리됨] |
| 같은 코드로 **두 번째 입금** | `REVIEW` | 첫 입금만 매칭. 두 번째는 환불 또는 운영자가 새 주문으로 연결 |
| 코드 없음 · 알 수 없는 입금자명 (닉네임 등) | `REVIEW` | 관리자가 [주문에 연결] 로 수동 매칭 |
| 알림 파싱 실패 | `REVIEW` (원문 보관) | 문구 변경 감지 신호이기도 합니다 → 관리자 알림 |

**환불은 사람이 합니다.** 토스 개인 계좌에서 자동 송금은 불가능하고, 해서도 안 됩니다. 시스템은 "환불 처리됨" 상태와 처리자만 기록합니다.

## 3. 지급 경로

### 3.1 흐름

```
입금 소스(A 알림 / D 버튼 / 나중에 C 웹훅)
   └→ MOOKI payment.js : 서명 검증 → 입금 기록 → 매칭
         └→ RCON (home 25576) : rucpay deliver <주문ID> 
               └→ RucCore PaymentService : DB 에 지급 기록 + 권리 부여 (멱등)
                     └→ 접속 중이면 그 서버가 10초 안에 반영 / 아니면 다음 로그인 때
         └→ 디스코드 : 유저 DM "지급 완료" + 관리자 로그 채널
```

### 3.2 왜 RCON 은 한 서버(home)로만 보내는가

> **구현에서 바뀜 (§9)** — 아래의 `ruc_pay_grant` · `applyPendingOnLoad` 는 만들지 않았습니다.
> 1차 범위의 지급이 전부 DB 를 주인으로 하는 것(칭호 · 우편 · 원장)이라 필요 없었습니다.

DB 가 공용이라 **어느 서버에서 써도 같은 곳에 기록**됩니다. 유저가 약탈 서버에 있어도 home 에서 기록하면 됩니다. 문제는 약탈 서버의 **메모리 캐시**가 모른다는 것인데, 이건 제재(§6.44)가 이미 푼 문제와 같습니다:

- 지급 내용을 `ruc_pay_grant` 에 **"미적용"** 으로 적습니다
- 각 서버가 `PlayerDataService.loadAsync` 에서 **캐시에 넣기 전에** 미적용 지급을 적용합니다 (`SanctionService.applyPendingOnLoad` 와 같은 자리)
- 접속 중인 사람은 각 서버의 10초 주기 확인이 집어 갑니다
- 적용 표시는 **조건부 UPDATE 먼저** (`WHERE applied_at IS NULL`, 갱신 행 1일 때만 적용) — 두 서버가 동시에 집어도 한 번만 들어갑니다 (§6.21 과 같은 구조)

### 3.3 상품 종류별 지급

| 종류 | 지급 방법 | 기존 코드 |
|---|---|---|
| 칭호 | `ruc_title` 에 `source = 'purchase'` | ✅ `TitleService.grantBlocking` — 디스코드 동기화가 지우지 않습니다 (§6.29) |
| 기간제 등급 (VIP 등) | 새 테이블 `ruc_entitlement(uuid, key, expires_at)`. 연장 구매는 `expires_at` 를 뒤로 미룸 | ❌ Phase 8 — 혜택 자체(채팅 색 등)는 아직 없음 |
| 아이템 · 코스메틱 | **우편함** (`ruc_mail`) | ✅ `MailboxService` — 미접속 · 다른 서버 · 인벤토리 가득 참을 이미 처리 |
| 디스코드 역할 | 봇이 직접 부여 | ✅ `roles.js` |

**우편함이 오프라인 대기열 역할을 합니다.** 지급 알림도 우편 한 통(메시지)으로 넣어서, 접속하면 "안 받은 우편 N통" 으로 보이게 합니다.

### 3.4 RCON 명령 (`/rucpay`, 콘솔 · RCON 전용)

| 명령 | 응답 |
|---|---|
| `rucpay deliver <주문ID> <uuid> <상품ID>` | `RUCPAY OK id=<지급ID>` / `RUCPAY DUP id=<지급ID>` / `RUCPAY ERROR <사유>` |
| `rucpay revoke <주문ID>` | `RUCPAY REVOKED` / `RUCPAY NOT_FOUND` (환불 시 기간제 권리 회수) |
| `rucpay status <주문ID>` | `RUCPAY STATUS <상태> applied=<0|1>` |

`DUP` 은 `ruc_pay_grant.order_id` 의 **UNIQUE** 가 만듭니다. "응답만 못 받고 실제로는 들어간" 경우에 재시도해도 두 번 지급되지 않습니다 — `rucsanction` 의 `ref` 와 같은 방식입니다.

## 4. 데이터 모델

봇이 DB 를 직접 만지지 않습니다 (기존 원칙). 주문 · 입금은 **봇이 RCON 으로 RucCore 에 기록**하고, RucCore 만 테이블을 씁니다.

> 대안 검토: 주문을 봇 쪽 JSON 파일(`sanctions_data.json` 처럼)에 두는 것.
> **채택하지 않았습니다.** 돈 기록은 백업 · MySQL 이전 · 5년 보관(§5.6)을 따라가야 하는데,
> 봇 폴더의 JSON 은 백업 대상 밖이고 gitignore 입니다.

```sql
CREATE TABLE ruc_pay_order (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  code         VARCHAR(8)   NOT NULL,            -- R4821
  discord_id   VARCHAR(20)  NOT NULL,
  uuid         CHAR(36)     NOT NULL,            -- 주문 시점에 확정 (D10)
  product_id   VARCHAR(32)  NOT NULL,
  amount       INT          NOT NULL,            -- 원
  status       VARCHAR(16)  NOT NULL,            -- 아래 상태 흐름
  created_at   BIGINT NOT NULL,
  expires_at   BIGINT NOT NULL,
  paid_at      BIGINT,
  delivered_at BIGINT,
  deposit_id   BIGINT,
  note         VARCHAR(255)
);
CREATE INDEX idx_pay_order_code ON ruc_pay_order(code, created_at);

CREATE TABLE ruc_pay_deposit (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  source       VARCHAR(16)  NOT NULL,            -- notify / manual / pg
  external_id  VARCHAR(64)  NOT NULL,            -- 소스가 준 ID, 없으면 원문 해시
  amount       INT          NOT NULL,
  depositor    VARCHAR(64),                      -- 입금자명 (= 코드가 정상)
  received_at  BIGINT       NOT NULL,
  raw_hash     CHAR(64)     NOT NULL,            -- 원문 SHA-256 (원문 자체는 봇 로그에)
  status       VARCHAR(16)  NOT NULL,            -- MATCHED / REVIEW / REFUNDED / IGNORED
  order_id     BIGINT,
  resolved_by  VARCHAR(20),                      -- 수동 처리한 관리자 디스코드 ID
  UNIQUE (source, external_id)                   -- 같은 알림 두 번 → 두 번째는 무시 (멱등)
);

CREATE TABLE ruc_pay_grant (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  order_id     BIGINT NOT NULL UNIQUE,           -- 주문당 지급 1회 (DUP 판정)
  uuid         CHAR(36) NOT NULL,
  product_id   VARCHAR(32) NOT NULL,
  created_at   BIGINT NOT NULL,
  applied_at   BIGINT,                           -- NULL = 아직 캐시에 반영 안 됨
  revoked_at   BIGINT
);

CREATE TABLE ruc_pay_log (                       -- 감사 로그. 지우지 않습니다
  id        BIGINT AUTO_INCREMENT PRIMARY KEY,
  at        BIGINT NOT NULL,
  order_id  BIGINT,
  deposit_id BIGINT,
  action    VARCHAR(24) NOT NULL,                -- ORDER_CREATE / DEPOSIT_IN / MATCH / DELIVER / DELIVER_FAIL / REFUND ...
  actor     VARCHAR(32) NOT NULL,                -- system / notify / <관리자 디스코드 ID>
  detail    VARCHAR(500)
);
```

### 주문 상태 흐름

```
           ┌──────────── 60분 ────────────┐
PENDING ───┤                              ▼
   │       │                          EXPIRED ──(7일 내 정확한 입금)──┐
   │ 입금 확인 (자동 매칭 / 관리자 승인)                              │
   ▼                                                                 │
  PAID ◄─────────────────────────────────────────────────────────────┘
   │ rucpay deliver
   ├──► DELIVERED ──(환불)──► REFUNDED   (기간제 권리 회수, 칭호 회수)
   └──► DELIVER_FAILED ──(재시도 버튼 · 5분마다 자동 3회)──► DELIVERED
PENDING ──(유저 /충전취소 · 관리자)──► CANCELLED
```

상태 전이는 전부 **조건부 UPDATE** (`WHERE status = '<이전 상태>'`) 로 합니다. 갱신 행이 0이면 다른 경로가 먼저 처리한 것입니다.

## 5. 보안

| 항목 | 방법 |
|---|---|
| **웹훅 서명** | 알림 앱 → MOOKI 요청에 `X-Ruc-Timestamp` · `X-Ruc-Signature: HMAC-SHA256(secret, timestamp + "." + body)`. `crypto.timingSafeEqual` 로 비교. 비밀값은 MOOKI `.env` 의 `PAY_WEBHOOK_SECRET` (gitignore) |
| **재전송(replay) 방지** | 타임스탬프가 ±5분 밖이면 거부 + `(source, external_id)` UNIQUE 로 같은 알림 재전송은 저장 단계에서 무시 |
| **멱등성** | 입금 = `(source, external_id)` UNIQUE · 지급 = `order_id` UNIQUE · 상태 전이 = 조건부 UPDATE. 어느 단계를 몇 번 반복해도 결과가 같습니다 |
| **엔드포인트 노출** | MOOKI 의 HTTP 서버는 웹훅 경로 **하나만** 엽니다 (`POST /pay/notify`). 본문 크기 제한 8KB, IP 당 분당 30회. RCON 포트는 여전히 열지 않습니다 |
| **관리자 권한** | [입금 확인] [주문에 연결] [환불 처리됨] 버튼은 `roles.json` 의 **Manager 이상**만. 누른 사람이 `resolved_by` · 로그 `actor` 에 남습니다 |
| **금액 위조** | 지급 판단은 **입금 기록의 금액**과 주문 금액 비교로만 합니다. 유저가 보낸 값(디스코드 입력)은 상품 ID 뿐이고 가격은 서버의 `products.json` 사본에서 읽습니다 |
| **로그 보관** | `ruc_pay_*` 는 삭제하지 않습니다. 전자상거래법상 대금결제 · 재화 공급 기록은 **5년 보관** 대상입니다. 알림 원문은 봇 로그 파일에 두고 DB 에는 해시만 (원문에 잔액 등이 섞일 수 있어서) |
| **개인정보** | 입금자명이 코드이므로 **실명을 수집하지 않습니다.** 계좌번호 · 비밀값은 저장소에 넣지 않습니다 (공개 저장소) |

## 9. 구현 결과 (2026-10-02) — 설계와 달라진 점

**지급 대기열(`ruc_pay_grant` · `applyPendingOnLoad`)을 만들지 않았습니다.** 코드를 열어 보니
칭호는 이미 DB 가 주인이고 다른 서버가 30초마다 다시 읽습니다(`TitleService.refreshOnline`).
우편도 DB 입니다. 1차 범위의 지급은 전부 "DB 에 쓰면 끝" 이라 캐시 적용 단계가 필요 없었습니다.
대신 지급의 각 단계를 **멱등**하게 만들어 같은 효과를 얻었습니다:

| 지급 | 두 번 해도 한 번인 이유 |
|---|---|
| 칭호 | `ruc_title` PK (uuid, 키) |
| 기간제 · 엔더상자 | `ruc_entitlement` 원장의 UNIQUE (주문, 키) — 현재 값은 합산 |
| 우편 아이템 | 사유에 `충전 R4501 #12` 를 적고, 있으면 보내지 않음 (`MailboxService.sendItemOnce`) |

**기간제 등급의 칭호는 디스코드 역할이 붙입니다.** VIP · SVIP · MVP 칭호가 이미 디스코드 역할과
연결돼 있어서(§6.27), 봇이 역할만 주면 칭호는 기존 동기화가 붙입니다. 끝나면 봇이 역할을 떼고
(`rucpay expired`), 칭호도 따라 빠집니다.

**상품표에 `available` · `grants` · `discordRoles` 가 생겼습니다** (`web/content/products.json`).
지금 판매 중인 것은 **후원 칭호(`supporter`) 하나**입니다. VIP 등은 혜택(Phase 8)이, 엔더상자
확장은 기능 자체가 아직 없어서 `available: false` 입니다 — 없는 것을 팔지 않습니다.
