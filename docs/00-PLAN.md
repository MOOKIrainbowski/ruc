## A. 현재 프로젝트 상태 (실측)

작업 폴더를 전부 스캔한 결과입니다. **빈 프로젝트가 아닙니다.**

| 항목 | 상태 | 비고 |
|---|---|---|
| `MOOKI(General-purpose Discord server bot)/` | **가동 이력 있음** | discord.js v14, 912줄 단일 파일. §4.1의 "이미 보유한 범용 봇" |
| └ 보안 모듈 | 구현됨 | 스팸/피싱링크/대량멘션/레이드(대량입장) 탐지 |
| └ 티켓 시스템 | 구현됨 | 문의/신고/건의 3종 — **§3.8 신고 시스템의 기반** |
| └ 반응 역할, 임베드 빌더, 채널설정 | 구현됨 | 유지 대상 |
| └ 경제 미니게임 | 구현됨 | 가입/출석/주식/창업/상장/인수/랭크/프로필 — **§4.1 제거 대상** |
| └ `.env` | **RCON 정보 이미 존재** | `MC_HOST` / `MC_RCON_PORT` / `MC_RCON_PW` 채워져 있음 → 어딘가에 MC 서버가 이미 있음(확인 필요) |
| └ `bot.log` | **크래시 상태** | `messageCreate` 핸들러에서 unhandled error → 프로세스 종료. 로그 경로도 구 위치(`Desktop\code\discord_bot\MOOKIbot`) |
| `ruc_server_icon/` | 준비됨 | `non_bacground.png`(투명배경 800×800), `common.png` |
| `web_background/` | 준비됨 | candidate_1/2/3.png (2559×1439 셰이더 스크린샷) |
| `conversation.md` | 0바이트 | 빈 파일 |
| 마인크래프트 서버 파일 | **없음** | 전부 신규 구축 |
| 웹사이트 | **없음** | 전부 신규 구축 |
| git 저장소 | **아님** | Vercel 연동 위해 §7.7에서 초기화 필요 |

### 즉시 발견된 문제 3가지

1. **MOOKI가 지금 죽어 있습니다.** `bot.log` 마지막 기록이 unhandled `error` 이벤트로 인한 프로세스 종료입니다. `client.on('error')` 핸들러와 최상위 예외 처리가 없습니다.
2. **`.env`가 평문으로 폴더에 있습니다.** 디스코드 토큰과 RCON 비밀번호가 그대로 들어 있고, Vercel 연동을 위해 git을 붙이는 순간 유출 위험이 생깁니다. → Phase 0에서 `.gitignore` 먼저, 토큰 재발급 권장.
3. **RUC 이름 충돌.** MOOKI 경제 미니게임의 화폐 이름이 이미 "RUC"이고 `/ruc지급` 명령까지 있습니다. 그런데 §3.1의 Ruc는 **마인크래프트 4개 서버 공용 화폐**입니다. 디스코드 주식게임 잔고와 인게임 Ruc가 같은 이름의 다른 화폐면 유저가 반드시 혼동합니다. → 결정 필요 (`02-OPEN-QUESTIONS.md` Q4)

### Phase 3 — 약탈 서버 (우선순위 1) — 구현 완료

- [x] `RucRaid`: **전투 중 접속 종료 → 재접속 시 강제 사망 + 아이템 전부 소멸 + XP 전부 소멸** (§2.4)
  - 전투 태그 15초 (`CombatTagService`). 화살·물약·TNT·길들인 동물까지 **최초 가해자를 역추적**해 태그합니다. 직접 타격만 보면 원거리·폭발 딜러가 태그를 피해 갑니다.
  - **양쪽 다** 태그합니다. 때린 쪽만 태그하면, 맞기만 하다 끊고 도망치는 경로가 그대로 열립니다.
  - 태그 상태로 종료 시 `ruc_raid_pending` 에 기록. 이 한 건만 **동기로** 씁니다 — 비동기로 넘기면 퇴장 직후 서버가 내려갈 때 기록이 유실되고, 하필 그게 콤벳로그를 하는 사람이 노리는 상황입니다.
  - 재접속 시 인벤토리 `clear()` **후** `setHealth(0)` (`ExecutionService`). **드랍이 남지 않는 것이 핵심** — 그냥 죽이기만 하면 불리한 싸움에서 끊고 안전한 곳에서 죽어 지인이 드랍을 줍는 쪽이 오히려 이득이 됩니다.
  - 자체 XP 0으로 초기화. 바닐라 XP도 0으로 만들어 경험치 구슬이 흩뿌려지지 않게 합니다.
  - **레벨은 유지** (`combat.execution-resets-level: false`). 레벨은 수십 시간짜리 누적이라, 한 번의 콤벳로그로 지우면 처벌이 아니라 그만둘 사유가 됩니다.
  - 태그 중 `/home` `/spawn` `/tpa` 계열 차단 (`/plugin:command` 형태의 우회 포함). 안 막으면 처형 규칙 자체가 무의미합니다.
- [x] `/spawn` `/sethome` `/home` `/delhome` + 한글 별칭 `/스폰` `/셋홈` `/홈` `/홈삭제`
  - 시전 5초 + 쿨타임 30초. 시전 중 한 블록이라도 움직이거나 피해를 입으면 취소됩니다.
  - `ruc_home` 키는 (uuid, server_id, name) — 서버별로 홈이 따로 있고, 나중에 다중 홈(D7 후원 혜택)을 열 때 스키마를 바꾸지 않아도 됩니다.
- [x] 드래곤 알 1개 배치 + 버프 (D3) — `DragonEggService`
  - 이득: 최대 체력 +4, 성급함 I, Ruc +15%, 자체 XP +10%, 비전투 10초 후 재생 I
  - 대가: 30초마다 발광 + 반경 200블록 알림, 하루 1회 전 서버 공지, **모든 컨테이너 보관 차단**(호퍼 우회 포함), 사망 시 무조건 드랍
  - 배치 판정은 월드에 알이 있는지가 아니라 DB 플래그입니다. 누가 들고 있는 상태를 없음으로 오해하면 알이 계속 복제됩니다.
  - 최대 체력 보정은 `addTransientModifier` — 서버가 비정상 종료돼도 알 없이 체력만 늘어난 계정이 남지 않습니다.
- [x] 에픽/보스 몬스터 XP 소스 — RucCore `PlayerListener` 가 이미 처리합니다 (보스 400 / 엘리트 60 / 일반 2)

  - **`transfer()` 에는 적용되지 않습니다.** `deposit()` 에 배수를 걸면 알 소지자에게 송금했다 돌려받는 것만으로 화폐가 늘어납니다. 번 돈과 받은 돈을 분리해 `reward()` 에만 적용합니다.

### 프록시 연결 (Velocity) — 완료

플레이어는 **25565(프록시) 하나로만** 접속하고, 거기서 4개 서버로 분배됩니다.

- Velocity **3.5.1** (build 615, RECOMMENDED). 원래 받아둔 4.1.2-SNAPSHOT 은
  **Java 25**(class file 69)를 요구해서 JDK 21 에서 실행되지 않았습니다. 3.5.1 은
  class 65(Java 21)이고, `velocity.toml` 의 `config-version = "2.7"` 도 3.x 형식이라
  설정을 그대로 씁니다. §6.2 "안정 우선" 결정과도 맞습니다.
- 프로토콜 확인: 클라이언트가 774(1.21.11)로 핑하면 774 를 그대로 돌려줍니다.
  지원하지 않는 값(999)을 보내면 자기 최대치인 776 으로 답하므로, 774 를 되돌려준 것
  자체가 1.21.11 지원의 증거입니다.
- `player-info-forwarding-mode = "modern"` + `forwarding.secret` (24바이트 랜덤).

**고친 것 — 인증 구역 좌표 불일치 (D10 구멍):** `verification.area` 가 `z=512.5` 를

### 고친 것 — 자체 XP 레벨업 (§3.4)

요구 경험치를 넘겨도 레벨이 오르지 않던 문제. 원인이 두 개였습니다.

1. **레벨업 판정이 `XpService.award()` 안에만 있었습니다.** 로그인 시 DB 에서 불러온
   값은 아무도 검사하지 않아서, 저장된 경험치가 이미 요구치를 넘긴 상태면 **다음
   경험치 획득이 있을 때까지 레벨이 멈춰 있었습니다.** 판정을 `normalize()` 로 떼어
   멱등하게 만들고, `award()` 와 접속 시점(`catchUp()`) 양쪽에서 부릅니다.
2. **진행바가 95%부터 꽉 찬 것으로 보였습니다.** `Math.round(progress * 10)` 이라
   0.95 가 10칸이 됩니다. 막대가 가득 찼는데 레벨이 안 오르니 버그로 보입니다.
   내림으로 바꿔 "꽉 참 = 레벨업 직전"이 실제와 맞게 했습니다.

검증: `normalize()` 사후 불변식(항상 `xp < 요구치`)을 xp 0~20000 × Lv.1~5 전 조합에서
확인 — 위반 0건. 멱등성도 확인.

점검용으로 `/rucxp <양> [닉네임]` (스태프)을 추가했습니다.

### Phase 3.5 — 네트워크 메뉴 (Shift + F) — 완료

**왜 Shift + F 로 되는가:** 서버는 클라이언트의 임의 키 입력을 볼 수 없습니다.
바닐라 클라이언트가 키 때문에 패킷을 보내는 경우는 정해져 있고, 그중 하나가
**F(손에 든 아이템 교체)** 입니다. 이건 `PlayerSwapHandItemsEvent` 로 잡히고,
웅크림 여부는 서버가 이미 알고 있으므로 "웅크린 채 F" = Shift + F 가 됩니다.
모드나 리소스팩 없이 되는 유일한 방법입니다. 이벤트를 취소하지 않으면 메뉴가
열리면서 손의 아이템도 같이 바뀝니다.

F 를 다른 키로 재배치한 사람을 위해 `/메뉴`(`/menu` `/서버`)도 함께 둡니다.

- `MenuService` (RucCore 소유 — 4개 서버 어디서나 동일하게 열립니다)
  - **서버 이동** 4칸. 현재 서버는 반짝임으로 구분하고, 각 서버의 접속 인원을
    같이 보여줍니다.
  - **내 정보** — 본인 머리 아이템. 레벨/경험치/Ruc/평판/KDA. 머리가 제 스킨으로
    보이는지로 스킨 로딩까지 한눈에 확인됩니다.
  - **인증 상태**, **언어 전환**(즉시 스코어보드까지 재번역), **스폰 이동**,
    **도움말**(전투 규칙 · 이동 방법 · 경제)
- `NetworkService` — 프록시와의 BungeeCord 채널. 서버 이동과 인원 조회.
  플러그인 메시지는 **플레이어의 연결을 타고** 나가므로, 접속자가 없으면
  인원 조회를 건너뜁니다.
- 메뉴 판별은 제목 문자열이 아니라 `MenuHolder` 타입으로 합니다. 제목은 언어와
  색코드에 따라 달라져서, 조금만 바뀌어도 클릭 차단이 통째로 풀립니다.

### 고친 것 — 스킨이 로드되지 않던 문제

**원인: 백엔드가 오프라인 모드였고 프록시가 없었습니다.** 오프라인 모드에는
모장 인증이 없으므로 프로필에 **텍스처 속성 자체가 들어오지 않습니다.** 그래서
모두 기본 스킨으로 보였습니다. 코드가 프로필을 건드린 곳은 한 군데도 없었습니다.

프록시를 붙이면서 `online-mode = true`(프록시) + `velocity.online-mode: true`
(백엔드 4개)가 되어, 서명된 프로필이 텍스처와 함께 전달됩니다.

**딸려온 문제 — UUID 가 바뀝니다.** 오프라인 UUID(버전 3, 이름 해시)와 정품
UUID(버전 4)는 다른 값이라 기존 데이터가 통째로 orphan 이 됩니다. 실제로
`M02ki` 의 디스코드 인증이 오프라인 UUID 쪽에만 붙어 있었습니다. 정품 UUID 행으로
이관했습니다 (`discord_id` 에 UNIQUE 가 걸려 있어 원본 쪽은 반드시 비워야 합니다).

### 고친 것 — 서버마다 DB 가 따로였음 (§3.1 위반)

4개 서버가 각자 `plugins/RucCore/data` 를 쓰고 있었습니다. 프록시가 붙기 전에는
드러나지 않았지만, 이동이 가능해지는 순간 **홈에서 인증한 사람이 약탈로 건너가면
그쪽에서는 미인증자**가 되고 지갑도 따로 놉니다. "Ruc 는 모든 서버 공용"이
성립하지 않습니다.

- `h2-file` 을 `../../../shared/ruc` 로 바꿔 4개가 같은 파일을 봅니다
  (H2 `AUTO_SERVER=TRUE` 라 여러 프로세스가 열 수 있습니다 — 애초에 이걸 위한 설정).
- 기존 데이터는 병합했습니다. 같은 사람의 오프라인/정품 행은 더 진행된 쪽을 살리고
  디스코드 연동을 정품 쪽으로 옮겼습니다. `ruc_raid_state` 의 `dragon_egg_placed`
  플래그도 함께 옮겼습니다 — **빠뜨리면 재기동 때 드래곤 알이 하나 더 생깁니다**
  (D3 는 네트워크 전역 1개가 전제).
- 4개가 동시에 기동하면 H2 잠금 경쟁으로 한두 개가 죽습니다
  (`FileLock.waitUntilOld`, AUTO_SERVER 의 알려진 경쟁 상황). `Database` 에
  지수 백오프 재시도를 넣고, 시작 스크립트도 어긋나게 띄우도록 했습니다.
  운영의 MySQL 에서도 같은 재시도가 재시작 직후의 연결 거부를 흡수합니다.

### 추가 요구사항 (2026-09-27) — 우편함 · 메시지 · 유저 상점 · 칭호 · 가이드

#### 인게임 채팅의 머리 아이콘 — 요구사항 그대로는 되지 않습니다

이 한 항목만 예외입니다. 먼저 적어 둡니다.

인게임 채팅은 **텍스트**입니다. 바닐라 클라이언트가 채팅 줄에 그릴 수 있는 그림은
리소스팩 폰트의 **글리프**뿐이고, 글리프는 리소스팩 안에 미리 들어 있는 정적
이미지입니다. 접속하는 사람마다 다른 스킨을 런타임에 글리프로 구워 넣을 방법이
없습니다 (클라이언트 모드를 요구하면 가능하지만, 이 서버는 §2 에서 바닐라
클라이언트로 접속하는 것을 전제로 잡았습니다).

그래서 두 갈래로 나눕니다.

- **디스코드 쪽은 진짜 스킨 머리가 됩니다.** 중계 웹훅의 아바타에 그 사람의
  머리 이미지를 걸면 됩니다. 이미 Phase 6 계획에 들어 있는 항목입니다.
- **인게임은 포맷에 `%head%` 자리를 지금 만들어 둡니다.** 리소스팩(9b)이 나오면
  그 자리에 칭호 색을 따르는 머리 실루엣 글리프가 들어갑니다. 리소스팩이 없는
  동안에는 **빈 칸으로 접힙니다** — 글리프가 없는 코드포인트를 내보내면 두부
  문자(□)가 뜨는데, 그게 채팅 모든 줄에 붙는 것보다는 없는 편이 낫습니다.

결과적으로 요구사항의 네 칸(`머리 · 칭호 · 닉네임 · 내용`) 중 **머리만** 런칭
시점에 비어 있고, 리소스팩이 붙으면 저절로 채워집니다. 포맷 문자열은
`messages_*.yml` 에 두므로 그때 코드를 고칠 일이 없습니다.

**같이 고친 유실 경로.** `GuildService` 의 주간 보상은 `claimWeekly` 로 "받았음" 을

H2 MySQL 모드에서 따로 돌려 검증했습니다.

**확인하지 못한 것** — GUI 클릭 경로 전부. 클릭이 필요합니다.
`conversation.md` §8.3 에 점검표를 만들어 두었습니다.

### 설계 판단 3가지

1. **수령은 DB 먼저, 아이템 나중.** 순서를 뒤집으면 넣은 직후 서버가 죽었을 때
   우편이 남아 복사가 됩니다. 반대 사고(표시는 됐는데 못 넣음)는 `unclaim()` 으로
   되돌릴 수 있습니다 — 두 사고 중 되돌릴 수 있는 쪽을 골랐습니다.
   수령 판정 자체는 `claimed_at IS NULL` 조건이 붙은 UPDATE 의 갱신 행 수로 합니다.
   4개 서버가 같은 DB 를 보므로 자바 쪽 검사로는 경쟁을 막을 수 없습니다.
2. **아이템 우편은 빈 칸이 하나 있을 때만.** `addItem()` 의 부분 성공을 우편 한 통
   단위로 되돌릴 방법이 없습니다. 빈 칸에 들어가는 한 뭉치는 항상 전부 들어갑니다.
   바닥에 떨어뜨리지 않습니다 — 약탈 서버에서 그건 분실입니다.
3. **직렬화는 국가창고와 다른 방식.** 창고는 빈 칸 위치를 보존해야 해서
   `BukkitObjectOutputStream` 을 쓰지만, 우편은 한 뭉치뿐이고 대신 **30일을
   버팁니다.** 그 사이 버전이 올라갈 수 있어 데이터 버전을 함께 적는
   `ItemStack.serializeAsBytes()` 쪽이 맞습니다.

## ✅ Phase 6-1 · 6-2 — 칭호 · 채팅 포맷 (완료, 2026-09-27)

Phase 6 의 첫 단계입니다. 요구사항으로 들어온 [칭호]와 [메시지] 두 덩어리이고,
디스코드 역할 동기화와 같은 통로를 쓰기 때문에 Phase 6 안에 넣었습니다.

### 착수하자마자 바뀐 것 — 6-0 은 이미 되어 있었습니다

계획서 A절과 `conversation.md` §9 는 "MOOKI 가 죽어 있을 수 있다 —
`client.on('error')` 와 최상위 예외 처리가 없다" 고 적고 있었습니다.
**코드를 열어 보니 다 들어가 있었습니다** (`MOOKIbot.js` 37~67행:
`client.on('error')` / `shardError` / `unhandledRejection` /
`uncaughtException` + `safeListener` 로 감싼 리스너들). D10 인증을 붙이던
즈음에 같이 고쳐진 것으로 보이고, `bot.log` 의 크래시 기록은 폴더를 옮기기
전 경로(`Desktop\code\discord_bot\...`)를 가리키는 옛 것입니다.

그래서 6-0 을 "확인" 으로 닫고 칭호부터 시작했습니다.

| 항목 | 내용 |
|---|---|
| 새 파일 (Core) | `TitleRepository`(`ruc_title`) · `TitleService` · `ChatListener` · `TitleCommands` |
| 새 파일 (봇) | `titles.js` — 역할 → RCON 푸시, 훑기, `/칭호동기화` |
| 명령 (게임) | `/칭호 [키\|자동]` · `/titlegrant <닉> <키> [source]` (스태프) |
| 명령 (RCON) | `/ructitle roles` · `/ructitle <discordId> <역할ID,...>` |
| 명령 (디스코드) | `/칭호동기화 [전체]` (역할 관리 권한) |
| 칭호 정의 | 17개 — 스태프 7 (§3.2) · 후원 6 (D7) · 부스트 3 (§5.2) · 가이드 1 |
| 채팅 | `%head%%title%%name%:` + 본문. MiniMessage 접두부 + Component 본문 |
| 표시 위치 | 채팅 + 탭 목록. **머리 위 이름표는 하지 않았습니다** (아래) |

### 설계 판단 5가지

1. **역할 → 칭호 판정은 마크 서버가 합니다.** 봇은 "그 사람이 가진 역할 ID" 를
   그대로 넘기고, 어떤 역할이 어떤 칭호이고 무엇이 더 높은지는 `config.yml` 의
   `titles.definitions` 가 정합니다. 판정을 봇에 두면 우선순위가 두 군데에 적히고,
   한쪽만 고쳐졌을 때 "디스코드에서는 관리자인데 게임에서는 일반" 이 됩니다.
2. **역할은 ID 로 넣습니다** (이름이 아니라). 이름은 바뀌고, 공백·쉼표가 들어가
   RCON 인자로 실을 수 없습니다. ID 가 UI 에서 안 보이는 문제는 봇이 기동할 때
   콘솔에 `[역할] <이름> = <ID>` 를 전부 찍어서 해결했습니다.
3. **회수는 `source = 'discord'` 인 것만.** 역할 하나가 빠졌다고 유료 칭호(Phase 8)나
   가이드 칭호(Phase 11)까지 지우면 돈과 성취가 사라집니다. 실제로 이 경로를
   시험했습니다 — 가이드 칭호를 준 뒤 "역할 없음" 을 밀어 넣어도 살아남습니다.
4. **플레이어가 쓴 글은 절대 MiniMessage 로 해석하지 않습니다.** 접두부만
   MiniMessage 로 만들고 본문은 이벤트가 준 Component 를 그대로 이어 붙입니다.
   본문까지 파싱하면 누군가 `<click:run_command:/...>` 를 채팅에 심어 다른
   사람이 누르게 만들 수 있습니다. 색 태그를 허용하는 것과는 차원이 다릅니다.
5. **머리 위 이름표(nametag)는 미뤘습니다.** 그쪽은 스코어보드 팀의 prefix 로만
   되는데 `ScoreboardService` 가 사람마다 개인 보드를 붙이고 있어서, 팀을 얹으면
   4개 서버 × 개인 보드마다 같은 팀을 만들고 지워야 합니다. 9b 폴리싱으로 넘깁니다.

### 요구사항 그대로 되지 않은 한 칸 — 채팅의 스킨 머리

채팅에 그릴 수 있는 그림은 리소스팩 폰트의 **글리프**뿐이고, 글리프는 리소스팩
안에 미리 들어 있는 **정적** 이미지입니다. 접속자마다 다른 스킨을 런타임에
글리프로 만들 방법이 없습니다. 그래서:

- 포맷에 `%head%` 자리를 만들어 두고 `chat.head-glyph` 를 **빈 문자열**로 둡니다.
  리소스팩(9b)이 나오면 그 글자를 넣으면 코드를 고치지 않고 채워집니다.
- 비워 두는 이유: 글리프가 없는 코드포인트를 내보내면 **모든 채팅 줄에 두부
  문자(□)** 가 붙습니다. 없는 편이 낫습니다.
- 디스코드 중계(6-3)에서는 웹훅 아바타로 **진짜 머리**가 나옵니다.

### 확인한 것 / 못 한 것

확인함 (RCON + DB):

- 4개 서버 전부 칭호 정의 17개 로드, 오류 0건
- `ructitle roles` → 연결된 역할 ID 목록을 돌려줍니다 (봇이 훑을 대상을 고르는 근거)
- 역할 ID 를 하나 임시로 물려서: 역할 있음 → `helper`(우선순위 800),
  역할 없음(`-`) → `guide`(100) 로 내려앉고 **helper 만 회수**됩니다
- `titlegrant M02ki guide guide` 로 준 칭호가 디스코드 동기화 후에도 살아 있습니다
- 미인증 디스코드 계정 → `NOT_LINKED` (오류가 아니라 정상 상태로 취급)

못 함 — **플레이어 접속이 필요합니다.** `conversation.md` §8.4 에 점검표가
있습니다. 채팅 한 줄의 실제 모양, 탭 목록, `/칭호` 클릭 선택, 그라디언트가

## ✅ Phase 6-3 — 채팅 중계 (완료, 2026-09-28)

§4.1 의 "서버 채팅 중계 봇" 입니다. **이름과 달리 절반은 봇이 아닙니다.**

| 방향 | 누가 | 어떻게 |
|---|---|---|
| 인게임 → 디스코드 | **플러그인** (`DiscordRelayService`) | 웹훅에 HTTP POST 직접 |
| 디스코드 → 인게임 | **봇** (`relay.js`) | RCON `/rucrelay` |

### 왜 인게임 → 디스코드를 봇이 하지 않는가

봇은 인게임 발언을 알 방법이 **로그 파싱**뿐입니다. 그런데 6-2 에서 채팅 줄에
칭호를 붙였기 때문에, 로그의 한 줄에서 어디까지가 칭호이고 어디부터가 닉네임인지
모호합니다. 게다가 봇이 꺼져 있으면 중계가 멈춥니다.

웹훅은 그냥 HTTP POST 입니다. 플러그인이 직접 보내면 **UUID·닉네임·칭호·본문을
정확한 값으로 들고 있는 자리에서** 그대로 나갑니다. 파싱이 없습니다.

부수 효과가 하나 있습니다 — **웹훅 URL 이 곧 채널**이라서, §4.1 의 "서버별 채널
매핑" 이 각 서버 `config.yml` 의 `relay.webhook-url` 한 줄로 끝납니다. 중앙에
매핑 표를 둘 필요가 없습니다.

### 반대 방향은 봇만 할 수 있습니다

디스코드 메시지를 볼 수 있는 것은 봇뿐이고, 마크 서버에 말을 거는 통로는
RCON 입니다. 그래서 `relay.js` → `/rucrelay <발신자> <내용...>` 입니다.

**`/say` 를 쓰지 않은 이유**: `/say` 는 대상 선택자를 해석합니다. 디스코드에서
`@a` 나 `@e[...]` 를 치면 플레이어 이름으로 펼쳐집니다. `/tellraw` 는 더
나쁩니다 — 남이 쓴 글이 JSON 으로 해석되면 클릭 이벤트까지 심을 수 있습니다.
`/rucrelay` 는 args 를 문자열로 이어 붙여 `Component.text()` 로만 감쌉니다.

### 반드시 있어야 하는 두 줄

1. **`allowed_mentions: {"parse": []}`** — 없으면 인게임에서 `@everyone` 이라고
   치는 것만으로 디스코드 전체에 알림이 갑니다. 문자열을 걸러내는 방식은 우회가
   많아서, 디스코드가 아예 해석하지 않게 하는 쪽이 맞습니다.
2. **`if (message.author.bot) return;`** (`relay.js`) — 플러그인이 웹훅으로 쓴 글도
   bot 입니다. 이 줄이 없으면 서버와 디스코드가 같은 문장을 영원히 되돌립니다.

### 속도 제한

디스코드 웹훅은 초당 몇 건으로 제한되고, 429 를 받은 상태로 계속 쏘면 더 오래
막힙니다. 그래서 큐(기본 200) + 일정 간격 발송(기본 10틱 = 0.5초, 초당 2건)이고,
429 를 받으면 응답의 `retry_after` 만큼 쉬었다 **다시 시도**합니다. 큐가 넘치면
오래된 것부터 버리고 종료 시 몇 건 버렸는지 로그에 남깁니다 — 채팅 중계가
밀렸다고 서버가 느려지는 것이 훨씬 나쁩니다.

### 확인한 것

로컬에 **가짜 웹훅 서버**(node http, 포트 8787)를 띄우고 홈 서버의
`relay.webhook-url` 을 그쪽으로 돌려서 실제로 나가는 것을 눈으로 봤습니다:

- 발언 모양 — `username` + `avatar_url`(스킨 머리) + `content`
- 시스템 모양 — `embeds[{title, description, color}]` (§4.1 의 "임베드로 구분")
- **`allowed_mentions: {"parse": []}` 가 두 모양 모두에 붙어 있습니다**
- 한글 UTF-8 왕복 정상, `Content-Type: application/json`
- 연속 발송 8건이 0.5초 간격으로 **하나도 빠지지 않고** 도착 (큐 + 페이싱)
- `/rucrelay test` — 운영자가 URL 을 넣고 바로 확인할 수 있는 점검 명령

봇 쪽은 순수 함수만 단위 확인했습니다 — 줄바꿈/탭 평탄화, 첨부 표시,
커스텀 이모지 `<:name:id>` → `:name:`, 발신자 이름의 공백 → 밑줄
(RCON 인자가 밀리지 않게), 256자 절단.

### 못 한 것

- **실제 디스코드 채널로 보내 보기** — 웹훅 URL 이 필요합니다 (소유자 작업, §13.4)
- 429 백오프 — 코드는 있지만 실제로 429 를 받아 보지는 않았습니다
- 디스코드 → 인게임을 눈으로 보기 — 접속한 플레이어가 필요합니다
